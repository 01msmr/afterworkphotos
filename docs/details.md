# afterworkphotos — details

How everything works, in detail. The overview is in the [README](../README.md).

## Files

| file | what it is |
|---|---|
| `index.html` | the page: title, empty `.main`, loads `res/main.css` + `res/main.js` |
| `res/main.js` | builds the photo sections; desktop scroll/keyboard UI and the touch-device sheet deck |
| `res/main.css` | desktop layout at the top, the whole deck nested inside `html.deck { … }` (native CSS nesting, Safari 17.2+) |
| `manifest.json` | web app manifest — required, see *iOS home screen app* |
| `img/awp-YYYY-MM-DD-NN.jpg` | the photos, square, 1000 px — named by date taken, NN counting that day's photos |
| `img/awp-….mp4` | a photo that is a video: 1000 px square H.264; the `.jpg` of the same name is its first frame |
| `img/thumb/awp-….jpg` | 200 px thumbnails, same crop — generated, for the overview UIs |
| `img originals/awp-….<ext>` | the originals at full size, cropped to the same square — **local only**, gitignored and never pushed: they keep the metadata (GPS included) the public images are stripped of. A photo ingested by the runner keeps no original past that run; the derivative and the thumbnail are what the repository holds |
| `photos.json` | generated index the page is built from: count, and per photo `n` (1 = oldest), `id`, `taken`, `place` (city-level, from the original's GPS — see *Adding a photo*), `desc` (1–3 word image description — see *Adding a photo*), `file`, `thumb`, `video`; and a top-level `places` block, place name → `[lat, lon]` of the town's centre (two decimals — public knowledge about the town, nothing about a photo), which lays out the wall map |
| `inbox/` | where new photos land (the Shortcut puts them there); emptied by the ingest workflow |
| `scripts/ingest.sh` | numbers an inbox photo, makes the 1000 px square, moves the original, bumps `PHOTO_COUNT` |
| `.github/workflows/ingest.yml` | runs the script on every push to `inbox/` and commits the result |
| `upload.php`, `secret.php`, `.user.ini` | the old server-side upload endpoint — superseded by the inbox, to be removed |
| `apple-touch-icon.png`, `favicon.ico` | icons |
| `card-stack.html`, `res/onepage.*`, `res/noRubberband.js`, `favicon_.ico` | legacy / prototypes, not referenced by the page |
| `docs/superpowers/specs/`, `docs/superpowers/plans/` | design specs and implementation plans of larger changes (the iPad deck / aspect layouts / precision scrubber of 2026-08-23 are there, with the browser checks each step was verified by) |

The file names are internal. The site shows photos as `afterworkphoto N` (a video as `afterworkvideo N`, same numbering), N being the position in date order from `photos.json` — which is the single source of truth for what exists; the page builds nothing until it has loaded it. Under each caption a quiet second line (`metaOf()`, `.meta`) gives the place and the date taken, language-neutral and lowercase — `markdorf, 2018-08-17` — from `place` and `taken`; whichever is missing is left out, and with neither there is no line. On the desktop wall the whole line is part of the print's light: a dimmed caption shows only `afterworkphoto N` — place, date and desc fade in with the print. The `desc` — a 1–3 word image description (`street sign`, `red rose`) — sits left-aligned opposite the caption (`.desc`), in the meta's size but the caption's color, **on the caption's own baseline**: the line is a flex row aligned on baselines (`p.subtitle`, with the name and its meta line wrapped in `.cap`), so the small type stands with the large instead of hanging above it — and like the place it belongs to the lit print: dimmed, it is gone; it is also the image's `alt` text.

## How the page works

### Which layout

`main.js` decides at load: a touch device (`navigator.maxTouchPoints > 0` — iPhone, iPad, touch laptops) gets the **deck** and the class `deck` on `<html>`, which switches the deck CSS on; a mouse-only machine gets the **list**. `TABLET` (`min(screen.width, screen.height) >= 700`; the iPad mini is 744 logical px, the largest iPhone 440) adds the class `tablet`. For testing, `?touch=1|0` and `?tablet=1|0` override both.

The title is fitted to its box (`fitTitle()`). On a phone the box is the print's exact width (the sheet's 3 px inset plus the prints' `--side` margin, 4 %, on both sides), centred; on a tablet and on the desktop it is a small box (≤ 340 px) whose `right` is that same `--side` margin, so its right edge is the rightmost print's — by construction, nothing is measured.

### Desktop — the wall

A single screen, never free-scrolled — and a gallery walk: the screens lie **side by side**, the newest print at the left, older to the right, and the wall is **switched** screen by screen, sideways — the phone's deck turned on its side. A wheel notch — vertical, or a sideways trackpad swipe; the dominant axis counts, the inertia tail is swallowed by a 350 ms lock, small deltas accumulate to 40 px — moves one screen, `PageUp`/`PageDown`/`Space` too; the glide between screens is programmatic and hand-driven (`stepRow()`, `glideTo()`, `animateTo()` — cubic ease-out, ~600 ms per screen: a prompter start than the browser's own smooth scroll), so there is no scrollbar and no snap fighting momentum. A moment (600 ms) after the wall comes to rest, the row on screen lights up as if selected from the keyboard, with the print's own slow fade. A glide to a print chosen on the knobs ends on **arrival at its target**, not on a pause in the scroll events (a long smooth scroll starts slowly enough to pause them), and the knob windows hold still for the whole ride. A far target is never a long ride: the wall **cuts** to one screen short of it and glides only that last screen in (`glideTo()`) — the same move as the scrubber cutting the deck, so every arrival looks the same, whether the print was 2 screens away or 80.

The wall itself is a material: **white plaster** (fine SVG-noise grain and soft trowel streaks) or **concrete** (cooler, cloudy, pores, a faint formwork line), both generated in CSS, fixed behind everything. **Clicking on empty wall switches the material**; the choice is kept in `localStorage` (`wall`). Photos per row follow the shape of the room the prints actually have (`perRow()` over `usableWidth()`, which subtracts the map and its list when they are up): taller than wide 1, wider 2, wider than 2:1 3; the prints keep their column's width whether or not the row is full (`.main[data-per-row=…] div.awbox`), so the oldest print, alone on the last screen, hangs the size of all the others with the second place left empty, and are never taller than `--wall-room` leaves. With the map up the room is scarce and `html.map-on` pulls the margins in (1.6 % / 2.6vw) so the prints keep their size; shut, the wall's own margins are back (4 % / 6vw). On resize the existing boxes are regrouped into new rows (`regroup()` — no image reloads) and the row that was on screen stays on screen. Every image sits on an opaque sheet of 12.5 % gray, exactly its size, so the wall's texture never shows through: unlit, the image is at 4 % over the gray (captions 20 %) with only a faint close shadow — the full spot-shadow and the light belong to the print that is lit (hover, or the row at rest). While the wall is in motion, hover must not light passing prints under a resting cursor (`body.moving`); the **arriving** row is exempt — its light begins only once the wall has come to rest (`approachTop` marks every step's arrival; the rest-settle lights), with the print's own fade — undimming 0.8 s, dimming 0.2 s — shadow and image moving identically. Hover works again when the wall rests (a 300 ms silence timer is the fallback trigger). Captions are 1.65× under the big prints. The title rests at 6 %, lights under the mouse in 0.9 s and **dims again over 8 s** — the resting rule's transition is the one that runs on the way back, the hover (and, on touch, `.lit`) rule keeps the quick one for the showing.

**The map — the MAP icon, grown.** There is no second map object: the small dark square at the lower left (`.mapgo`, the knobs' mirror on the `--side` line) *is* the map. It is a quarter of a town seen from above, drawn in **streets alone** — two through roads north and south, a few lanes, a river along the bottom — and three of those streets fill the square: a serpentine climbing in switchbacks, a triangular block with its connecting lane, a dead end whose bowl returns to the stem. They run between the through roads the way any street does, the lanes come up to them and stop there, nothing crosses them and nothing runs parallel beside them, and nothing is built inside them; only the width of the line tells the three apart. Read as letters they say **MAP**.

Shown and hidden by a click on it, by Enter on its Tab station, or by the key **`m`**: it **scales fivefold from its own bottom left corner** (`transform: scale(5)`, `transform-origin: bottom left`), so that corner and both those edges stay exactly where they are and the growth is one smooth movement rather than a re-layout — 0.6 s, the same curve the sections use to open the room at their left. The prints shrink the same way: their top and right edges stay (`justify-content: flex-end` on a top-aligned row), and every section opens `--map-grown` plus the list plus a margin of room; nothing is measured, the CSS shares the geometry. The plan carries no edge of its own at any size: it says where it stands by lighting up — 12 % at rest, full under the mouse or on its Tab station. **It is not switched on and off, it is large while it has attention**: `Tab` into its station unfolds it, `Tab` or `Escape` away folds it up, and `m` steps in and out — the knob unit has always behaved this way. The mouse has no `Tab`, so for the mouse a click on the plan opens and shuts it and nothing else does: moving the mouse elsewhere leaves it standing (the plan and its list are exempt from the takeover, as the knobs are). Nothing is remembered between visits.

**Beside** it stands the plain list of the towns the archive knows, alphabetical, no numbers, no bullets, in the descriptions' own size (`--meta-size` — never smaller), its foot on the plan's foot and **never taller than the plan**: the names fill one column to that height and start the next (`column-fill: auto`), so a growing archive takes more columns rather than more height. It is its own element, so the map's 1.8 zoom does not reach it. A click on a town cuts the wall to its newest print and lights it; further clicks walk through that town's prints (`goToPlace()`), and the map stays up throughout — one can go from town to town without ever losing it. From the map's Tab station the **arrows walk the list** — up and down along a column, left and right from column to column (`townRows()` counts a column's names off the rendered list, since the browser decides how many columns the width takes) — the town under the mark set in bold and wearing two things the others hide: **how many prints come from there**, and a small **Enter key** — the return sign cut out of a black cap (`--towns-mark` on `--towns-paper`), no taller than the line, so nothing shifts when the mark moves. `Enter` or `Space` goes to that town — the same move the click makes — and the count then tells which of its prints one is looking at, 1 … max and round again. Leaving the town, or letting go of the map, sets the count back to the town's total and forgets the place in it, so coming back starts at its newest print. They never fold the plan up — the station holds it: they go to the town under the mark (Shift+`Enter` walks that town's prints the other way), or take hold of the first one if the arrows have not moved yet. The key goes down as one strikes it — a pixel and a half along its own diagonal, into the little shadow it stands on. Prints without a place are not on the list. The choice is kept in `localStorage` (`map`); a visitor who left it up sees it unfold as the gallery opens.

**Favs — what the visitor keeps.** The key **`f`** stars the print in hand — the lit one, or the one the knobs point at while they hold the station — and takes the star back. The count stands at the **left end of the title's own row**, flush with the left print wherever the wall begins — one variable, `--wall-left`, carries that edge to the prints and the title alike, and the map pushes it right when it is up: on the wall the title is a line with two ends (`.titlerow`, the mark and `.titlebox` sharing it), so the two share a baseline because they share a line — nothing is computed and nothing measured. The row is centred in the band above the prints (`--wall-top`), so it has as much air over it as under it. Under the mouse **and on its Tab station** its **type** comes up to the title's own size (`--title-type`, which both are set from) — the letters grow, the box does not: the line height is fixed, so the baseline and the title beside it do not move by a pixel. It reads `favs 7` — the name bold, the number behind it not; it is not there at all while nothing is kept, and at 28 % until the mouse is on it. A kept print says so with a small `★` **before its description**, at the left end of the caption line — and the star has the count's own motion: it is a slot of animated width (`.desc::before`), folded shut on an unkept print and opening, width and opacity in one 0.35 s transition, when `f` keeps it, the description sliding right by exactly the star's width; dropping folds it shut again. No overflow clipping on the slot — that would move an inline box's baseline off the caption's.

The numbers — nothing else — live in `localStorage` (`favs`) **and in the address**: `#154&f=3,17,88`, the shown print first, the kept ones after it. A bookmark therefore carries a whole selection from one visit to the next, or to somebody else; opening such a link adds its numbers to what is already kept rather than replacing it. Once something is kept, the favs join the **`Tab` round as a fourth stop**, where every step stays among them — the arrows walk them and so do `Enter` and `Shift+Enter`, the wall going to each as one steps, **newest first and oldest last**, the wall's own order (the numbers run the other way, so the walk does too). Arriving among them lights the **kept print nearest the one in view** and names it, so the walk carries on from where one stands — the mark counts along from that moment, `favs 7/24` — the figure one stands on **bold**, how many there are **light** behind a small stroke, the total always at the resting size. The number a fav wears **counts the way the prints do, the oldest being 1**, while the walk itself still runs the wall's way, newest first — so stepping on counts down, as it does on the wall. The count is built once and only its figures change, so it can move — and it moves **as one number**: a slot of animated width holds it whole, as many figure widths wide as the number has figures, and when the number takes a figure more or less the slot opens or closes by exactly one figure in one transition at its left edge, the stroke and the total riding along. The number is set flush right inside the slot, in the flow — so it shares the row's baseline outright with the name, the total and the title (all four measured on one line), and its figures keep their places while the slot's left edge moves; tabular figures make a figure width a figure width. No rolling drums, no cells — one number, one movement. The mark keeps one box while its type grows, so the row is not laid out again on every frame — and `f` drops the one in view; the guide gains their group.

**Jumping to a number — `j`.** On the wall `j` and the digits that follow name a print, `Enter` jumps (digits alone still do the same, as they always did, showing in the knobs' date window); at the favs stop the same keys name a **fav** by its number, the oldest being 1. The digits go into a **real `<input>`** (`.jumpbox`) that takes the focus after `j` — so they are the field's and never the browser's (a bare keydown handler loses digits to whatever the browser binds them to). The field looks like nothing but the figures: no border, no outline, no background, the title's own size and weight. It **stands in the title's row**, between the favs mark and the name of the place, and so shares that row's baseline outright — favs, count, title and the typed number measure on one line — and its **right edge is the left print's right edge**: its width is one column (`--col`, stated once per `data-per-row` from the same variables the prints use) less the favs mark's fixed width, with the row's gap at 0 so nothing has to be subtracted. At the favs the mark's own count shows the number too, as the place it will land. The key that opened it stands before the figures as a **`j` cap** (`.jumpbox .keycap`, the guide's kind, in the title's size, on the row's baseline by the letter's own), the cursor blinking in the field beside it; three seconds after the field opens the cap steps back to half (`@keyframes capdim`, restarted each time the box opens) — the figures are what matters. The field is there only while typing and goes with `Enter`, `Escape` or 4 s of silence. The guide lists `j 0–9 jump` in both groups.

Two things this uncovered: `fitTitle()` no longer runs on the wall — the title is set in `--title-type` and takes the width it needs, so there is nothing to fit, and the search only drove the `h1`'s own size to its ceiling, which every em in the row inherited; and the title row has no gap, the name keeping the right end by an auto margin.

**Input — the last-used one wins.** A keypress takes over from the mouse (keyboard mode, hover yields); real mouse movement (not jitter, not over the knob unit) takes over from the keyboard — the selection light drops and hover rules again. Keyboard: three toggles — **`b`** the background (the wall's material), **`n`** the navigation (the knob unit put away entirely, `html.nav-off`, kept in `localStorage`; `Tab` still walks all five stations — the unit shows while one of its two is focused), **`m`** the map. `Enter` (or `Space` — it never pages; `PageUp`/`PageDown` do) enters keyboard mode and steps the selection, arrows move (up/down by a screen), digits + `Enter` go to a number, `Escape` leaves. **`Tab` circles three stations**: the wall's lit print → the go-to knobs → the map → back (Shift+`Tab` backwards). The **guide** is no panel that covers anything: a line of key caps at the foot of the wall showing what the station one holds answers to, each group named after the place it belongs to — *at the knobs* `↑↓ year, ←→ print, ⏎ go`; *on the map* `↑↓←→ towns, ⏎ visit, ⇧⏎ back` — and, standing on the guide's own stop, all four groups at once — *on the wall* (`⏎ next, ⇧⏎ back, j 0–9 jump, f favorite`), *at the knobs*, *on the map*, *anywhere* (`m` map, `n` knobs, `b` wall) — set side by side in columns, each under its heading, one move to a line. Every key has its own cap, as on the board (`⇧` and `⏎` are two caps, not one), and a cap has a **key's silhouette**: square for one sign — a letter, an arrow — with corners rounded at a fifth of the side, the glyph big and centred with air around it, a thread of light along the top edge and the shadow straight under; `0–9` is as wide as it needs. A cap is no taller than the type beside it (the sign at 0.7 em, its box 1.45 of that). The caps of a group share a width so the words line up. The guide does not explain itself: the `?` is not in the list. The station hints show themselves **for one turn of the round**: after four `Tab`s the hand knows them and they fall quiet, while the guide's own stop keeps answering. Nothing marks it on the wall and it has no stop of its own: it greets whoever arrives at the **first station** — the wall's — with every group at once, and goes again after five seconds — fading out over 0.9 s, three times as slowly as it came, so it never blinks out mid-sentence. **Twice a day is enough**: the tally lives in `localStorage` (`guide`) under the day it belongs to and starts over tomorrow. The key **`?`** calls it up whenever one likes, as often as one likes, and the tally does not apply. It stands at the very foot of the window, 8 px off the edge, in 66 % black — there when looked for, never louder than the prints. On the very first visit the three always-keys show themselves once and go at the first touch of anything — `localStorage` (`guide`) sees to it that they are not shown again. The two knobs share one station and the **arrows tell them apart, along the axes they lie on**: `ArrowUp`/`ArrowDown` turn the year, `ArrowLeft`/`ArrowRight` the print (down and right go back in time), `Enter` commits the ride. The wall's material had a station of its own too; it is commented out of the round (the lines marked *station 4* in `main.js`), while the key **`b`** switches plaster and concrete as before. A focused knob **inverts** — dark machined face, light index, its window dark with light figures — inside a 6 px ring standing 4 px off; `ArrowUp`/`Down` (or left/right) turn it — down is older — and `Enter` commits the ride. The focused wall shows a 6 px dark border just inside the screen; arrows or `Enter` switch its material. While the keyboard is in use the knob unit hides. The mouse cursor is replaced by a small white dot.

**Go-to — two knobs under the wall.** A small machine fixed at the lower right, its right edge on the prints' `--side` line, shown at 1.8× (`.goto`, built in `main.js`; at rest it is only a 6 px dark line — the elements rise under the mouse; the line vanishes the instant they rise and returns only once they have fully dimmed): a **year knob** under a window of four rolling digit drums, a **print knob** under a window with the number and the same place-and-date line the captions wear (a long one ends in an ellipsis), and beside them the print's **image** in a window (white paper until the first turn). The wheel over the unit reads the same two axes the arrows do — **up and down is the year, sideways is the print**, whichever knob the pointer is on — and dragging a knob vertically turns it too (14 px per step, pointer captured; a real drag never commits). One mouse notch (or 24 px of trackpad) is one step: a year step lands on that year's newest print, a print step moves one print, carrying into the next year at the ends; **past either end both wrap around**. The rotation is honest and absolute: both angles are computed from the shown print alone (`showGoto()`), never accumulated, so a given print or year sits at the same angle however it was reached — turned to, scrolled to, deep-linked, typed — and the newest print, the start, is at the top of both dials. One revolution of the year knob spans the full calendar range, older years clockwise, an empty year costing its share of the circle; the print knob turns 3.6° per print, one revolution per 100. When a photo is added the whole scale advances one notch, like a counter. Nothing moves while the mouse is on the unit; **when it leaves**, the wall scrolls to the print and lights it (`goNow()` → `select()`, the keyboard path). Clicking the image goes at once. Typing digits puts a number into the date window, `Enter` goes. Scrolling the wall by hand rolls the windows to the row on screen. Like an unlit print the unit sits at 10 % until hovered. The knobs are CSS only (machined aluminium: brushed ring, turned centre, bevelled rim, engraved index; `--a` turns them). The VR gallery gets the same two knobs on its elevator panel.

### Touch devices — the sheet deck

The newest photo is on top, like a pile of daily prints. A sheet carries `K` photos — one upright, two side by side when the device is held sideways (`sheetsPer()`; 43 % prints, a gap of 1.5 side margins between them; on a phone the prints are bound by the height and centred). Upright, the phone takes the **wall's own arrangement**: a band of fixed height above the print (`--title-band`, 44 px — the phone's `--wall-top`) holds the title in its middle with a little air over and under it, the words at the right with their right edge on the print's right edge; the sheet starts its print at the band's foot (`padding-top: calc(var(--title-band) - var(--inset))`) — stated once, read by both, nothing measured. The words are fitted (`fitTitle()`) to a box **58 % of the sheet**, not the whole of it, which had made the title far larger than on any other device. The sheet centres its print itself (`justify-content: center` in the deck's own `section` rule): the wall's row starts at the left so a lone print keeps its column, and the sheet must not inherit that. Turning the device rebuilds the pile with the same photo on top (`rebuild()`, on `resize`; a move in flight is landed first). The deck works on sheet indices (`S = ceil(N / K)`, `photosOf(i)`), the scrubber on photo indices (`sheetOf()` maps between them). Swiping up lifts the top sheet off and uncovers the one before; swiping down pulls the newer sheet back on. Only seven sheets exist in the DOM at a time — the top one and three either side, built as they enter that window and dropped as they leave it, images loaded ahead — so a pile of hundreds costs what a pile of seven does (`WINDOW`, `sheet(i)`, `layout()` in `main.js`). Tapping does the same: the upper part of the screen goes forward, the lower part back — the boundary is the thin dotted line printed on every sheet (`--divider-y`, set from the photo's position). The last sheet wraps to the first; it is the same move as any other, there are no clones.

**A sheet pulled down enters paper first.** A backward move starts the sheet with its bottom edge 2 px above the screen (`travel = bottom + 2`; lifting off it is `bottom + 220`, the shadow's length), so the swipe shows paper from its first pixel instead of spending 220 px on shadow. The long shadow rises **with the entry, not with time**: `updateReveal()` sets `--shade-in` (0…1 over the first `SHADE_IN = 100` px the sheet is on screen) and the mover's box-shadow alphas are multiplied by it; lifting off it is 1 throughout.

**Edge scrubber.** The outer 28 px of the screen at **either edge** (below the status backdrop) is the pile seen edge-on — two strips, `.scrub` and `.scrub.left`, the same pile for whichever hand holds the phone; `side` (+1 right, −1 left) mirrors the label, the hint and the gears (at the left, finer is a slide to the **right**). A touch there **arms** it and it scrubs once the finger has been down **120 ms** (`ARM_MS`, `engage()`): a touch that lifts before that, or moves more than 20 px sideways off the strip within it (a swipe begun at the edge, `ARM_SIDEWAYS`), was never a scrub — that is how a stray touch is told from the real thing; the position is taken where the finger is when the time is up. Engaged, it opens: a strip of sheet edges with the years marked (marks that would land within 18 px of the previous one are left out), and beside the finger the photo under it: one 72 px print with its number on it, bottom left, white with a 2 px dark outline under the fill, 1 px showing (inverted in dark mode — `--number`, `--number-edge`), no card, no month. The label stands clear of the year marks (`labelRight`, from the widest mark) and clear of the thumb: its right edge keeps 44 px left of the touch point (`THUMB` in `placeLabel()`), following the finger into the gears. Dragging runs through the photos (top = newest); letting go cuts the deck to the sheet holding that photo — the top sheet lifts off straight onto an older target, a newer target comes down straight onto the top sheet.

*Resolution.* `neighbourCount(px)` — `≥ 6 px → 1, ≥ 2 → 3, else 5`, `px = stripHeight / N / rate` — no longer draws neighbours (the label was five prints until 2026-08-28; one is easier on the eye); it only says whether the strip skips photos, which is when the `← finer` hint shows. At the strip's ends the label is pushed inward to stay on screen.

*Precision gear.* Engaged only when the strip is too short for single-sheet hits (`pxPerPhoto < GEAR_NEEDED_PX = 6`): sliding the finger left off the strip and on scrubbing there slows the pile — 1× on the strip and up to 60 px in, ¼ from 60 px, 1/16 from 160 px (`gearRate()`). Under the label one hint, a small chip on paper, its arrow pointing **the way the finger is moving** and the word what lies that way — `← finer` towards the middle, `coarser →` back towards the strip (`hintDir`; mirrored at the left strip; at rest it points towards the middle) — shown whenever the gears are on and the strip skips photos or a gear is in. The touch-down sets the position from the strip; once a finer gear has been used the position follows the finger's travel (`scrubPos`), and `px` is divided by the rate. Capacity: single sheets are reachable while `16 · stripHeight / N ≥ 3 px` — comfortably to ≈ 1 900 photos on an iPhone, ≈ 2 900 on an iPad in portrait; a further gear (1/64) in `gearRate()` would multiply that by four. `startMove(dir, target)` is the same move as a swipe, just not to the neighbour; the sheet being uncovered (`.under`) sits above the resting pile (z 4) so the pile's own next sheets never show through during the cut.

Loading, so nothing looks empty: all thumbnails are fetched in the background once the page is up (batches of eight, `preloadThumbs`); every print has its thumbnail as a background, so a sheet still loading already shows its picture softly; the small print under the finger only ever shows a thumbnail that is already decoded (an `<img>` would otherwise keep showing its previous picture until the new one arrives) and stays blank paper until then; and when the finger rests on a sheet for 200 ms its full photo is fetched ahead (`warmUp`), so it is in the cache by the time the pile is cut to it.

**Videos** are captioned `afterworkvideo N` (`captionOf()`; the numbering is the photos'), and play only while on screen: in the deck while their sheet is the top one (paused in `layout()` otherwise), on the desktop while the print is lit — the pause lands only once the leaving print's 0.2 s dim has finished, so a video never freezes mid-fade. No autoplay.

What is on screen, always: the **top sheet**, 3 px in from the phone's edge with its paper edge showing, and the **two sheets beneath it**, full size and flat, so the top sheet's edge always shows paper around it. Stack positions are the classes `current`, `next`, `next2`, assigned by `layout()`.

A move, in `main.js` terms:

- `startMove(dir)` picks the `mover` (the top sheet to lift off, or the previous one to put back) and the `under` sheet it uncovers or covers. `travel` is measured from the mover's real position — the distance it needs to clear the screen, shadow included.
- While the mover is in the air it is always sheet-size (3 px inset, lifted shadow). The sheet beneath stays flat until the mover's bottom edge has cleared the lower 30 % of the screen (`revealAt`), then takes sheet size too — all four edges move in very slightly — and goes flat again on the way back. `updateReveal()` reads the mover's actual transform, so drags and the animated settle behave the same.
- `settle(commit, seconds)` animates the rest of the way in `seconds`, set on the sheet as `--settle` (the CSS transition reads it): 1.2 s from the scrubber, keys and deep links (`SETTLE`), 1 s from a tap (`TAP_SETTLE`), and after a swipe **the finger's own speed** — the last ~100 ms of the drag (`sample()`, `releaseVelocity()`) give a velocity, the rest of the way takes `distance ÷ velocity`, clamped 0.25–1.2 s: a flick lands fast, a slow push slowly, a finger that stopped before letting go gets the paper's pace. `finish()` re-assigns the stack and clears `--settle`. A finger that comes down in the **last 15 % of a settle** lands the move at once and is taken as a new gesture (`landIfNearlyThere()`, `EARLY`), so swiping early is never held up; earlier than that the touch is ignored. A 2.5 s watchdog covers a `transitionend` that never arrives (backgrounded tab).

The look is CSS only, all tokens on `html.deck` (`& { … }` at the top of the deck block):

- **Paper**: `#dedede` with a fractal-noise grain (inline SVG, ≤ 10 % alpha, seamless at 120 px). Dark mode via `prefers-color-scheme`: `#2b2927` paper, light ink, white title — same rendering, different tokens.
- **Paper edge** (`--sheet-edge`): 1 px lit bevel top/left, 1 px dark thickness line, 1–3 px contact shadow. Sized for a very small rounded object.
- **Letterpress print**: the photo sits in a recess — inset shadow on its top/left wall, a lit paper lip below. 6 px corners. No drop shadow.
- **Corners**: sheet corners are concentric with the phone's own; a sheet lying flat has square bottom corners (the glass rounds them). The phone's radius comes from `SCREEN_RADII` in `main.js` (per model, e.g. iPhone 16 → 55 px) with a CSS fallback derived from `safe-area-inset-bottom`.
- **Title on the pile**: `h1.title` at z 5 — above the resting sheets (z ≤ 4), under the one in the air (z 10), so a lifted sheet slides over the words and they show again printed on whichever sheet is on top.
- **Viewport height**: `--app-height` is `100lvh` in the CSS, never measured — see *iOS home screen app*.
- **Status bar backdrop** (`.main::before`): an opaque black strip the height of the status inset plus `--top-gap` (12 px — 22 left clean black under the blur, 6 let the blur reach the paper; 17e, 2026-08-28), with two convex corner fills in the phone's radius. Sheets start below it and slide under it, corners and all. The desk (`html, body`) is black so the Dynamic Island disappears into it.

## Adding a photo

Put an image into `inbox/` on `main` — that is all. The ingest workflow (`.github/workflows/ingest.yml` → `scripts/ingest.sh`) takes it from there:

1. writes the 1000 px square derivative — auto-oriented, centre-cropped (a no-op for a square), JPEG q85, metadata stripped so no GPS reaches the public image;
2. keeps the original at full size in `img originals/` — cropped to the same square (quality 95, metadata intact); one that already is square is moved untouched. **Originals stay on the machine that ingested them**: `img originals/` is gitignored, so nothing with GPS is ever pushed — a photo ingested by the GitHub runner leaves no original behind (the owner's own backups hold those);
3. **names every photo by its date taken**, `awp-YYYY-MM-DD-NN` (EXIF `DateTimeOriginal`, the QuickTime creation date for a video; undated ones become `awp-undated-NN` at the end). A photo the last `photos.json` already knows keeps that date without being measured again — its name encodes it, and re-reading every EXIF would cost minutes of every run once the archive has hundreds of photos; to force a fresh read, drop the photo's line from `photos.json`. An arrival earlier in a day than existing ones renumbers that day — derivative, original, thumbnail and video are renamed with `git mv`, so history follows;
4. makes any missing 200 px thumbnail (from the derivative, so it is the same crop) and rewrites `photos.json` from scratch — asking Nominatim (OSM) once per new photo for the city-level `place` of the original's GPS (English names; `city → town → village → municipality`; carried forward from the previous `photos.json` by date taken, so the network is only asked about photos it has never answered for). Only the name is published, never a photo's coordinates — what the same answer also yields is the **town centre's** coordinate, kept two-decimal in the `places` block for the wall map; a failed lookup stays `null` and is retried on the next run; a place can also be set or corrected by hand in `photos.json` — the next run carries it forward like any cached one. The same run asks Claude (Haiku, `describe()`) for a 1–3 word `desc` of any photo lacking one — needs the `ANTHROPIC_API_KEY` repo secret (and `jq`); without it descs simply stay `null`, and hand-written ones are carried forward the same way;
5. commits `photo awp-…`, pushes. The server pulls; live within seconds.

**Videos** (`.mov`, `.mp4`, `.m4v`) up to 30 s (`MAX_VIDEO_SECONDS`) go through the same steps with ffmpeg: a 1000 px square H.264 `img/N.mp4` with audio kept, its first frame as `img/N.jpg`, the full-size square original as `N_original.mp4`, date from the QuickTime creation date. Longer ones are moved to `inbox/too-long/`. A Mac without ffmpeg leaves videos in the inbox for the runner. The page plays them muted, looping, inline, swapped in once `photos.json` has arrived.

A photo's number on the site is its position in date order, so adding an old favourite shifts the numbers after it. The pile reads chronologically — newest on top, oldest at the bottom.

The workflow can also be run by hand (*Actions → ingest photos → Run workflow*) to regenerate thumbnails and `photos.json` with an empty inbox.

Runs are serialised, so two uploads can never both become the same name. A commit made by the workflow does not trigger it again.

The phone does this with a Shortcut that PUTs favourited photos into `inbox/` through the GitHub contents API (`PUT /repos/01msmr/afterworkphotos/contents/inbox/<yyyyMMdd-HHmmss>.jpg`, body `{"message":"inbox","content":"<base64>"}`, a fine-grained token with *Contents: read/write* on this repo only). It remembers what it has sent in a text file in iCloud Drive, so re-favouriting an old photo still works and un-favouriting never deletes anything.

By hand: `git add inbox/whatever.jpg && git commit && git push` does the same. To try the script locally: `scripts/ingest.sh` (needs ImageMagick), then look at what it staged.

`upload.php` is the old way — it edited `res/main.js` on the server, which the next pull undid — and is to be removed.

## Deep links

`#154` opens print 154 — on the desktop the wall opens on its row, lit, knobs synced; on a touch device the deck opens with its sheet on top. `#y2017` opens that year's newest print; the year always wears its `y`, so photo numbers and years can never collide, whatever the pile grows to. As the shown print changes (keys, knobs, scrubber, swipes), the address follows via `history.replaceState` — always copyable, never polluting the back button. A later hash change (pasting, back/forward across pages) glides/cuts to its print. Path forms (`/154`) would need an nginx rewrite (`try_files $uri /index.html;`) before the page could read `location.pathname`; the hash needs nothing.

## Deployment

Push to `main`; the server (nginx) pulls automatically within seconds. The page is `index.html`, `manifest.json`, `res/main.css`, `res/main.js`, `photos.json` and the images. The host serves `manifest.json` as `application/json` — keep the `.json` name, a `.webmanifest` may come back as `octet-stream` and iOS then ignores it.

**Caching.** The server sends no `Cache-Control`, so browsers — and the installed app most of all — keep old files on heuristics. `index.html` references `res/main.css?v=…` and `res/main.js?v=…`: **bump that version whenever CSS or JS change**, or the phone keeps the old code. `photos.json` is fetched with `cache: no-cache`, so it revalidates on every open. What the repo cannot fix is a stale `index.html` itself; the cure for that is one nginx line, `add_header Cache-Control "no-cache";` for `/index.html` (and `/`), after which a changed page arrives on the next launch and an unchanged one costs a 304.

Check a deploy from anywhere:

```sh
curl -s "https://afterworkphotos.com/photos.json?cb=$RANDOM" | python3 -c "import json,sys; print(json.load(sys.stdin)['count'])"
```

## Local development

```sh
python3 -m http.server 8765 --bind 0.0.0.0     # then open http://<your LAN IP>:8765 on the phone
```

Send `Cache-Control: no-store` if you iterate on the phone — iOS caches hard. Mind that another project's server on `127.0.0.1:8765` wins over `0.0.0.0:8765` for localhost requests.

The deck is chosen by touch support, not width — on a desktop browser use `?touch=1` (and `?tablet=1` for the iPad layouts) in a narrow or iPad-sized window, or an iframe of that size. The page needs `photos.json`, so it must be served, not opened as a file.

**Checking behaviour without a device.** There is no unit test runner. `tests/deck.html` is the deck's check page: it loads `index.html?touch=1&tablet=0` in a 390×844 iframe and drives it with synthetic `TouchEvent`s — viewport, title stacking, swipe/flick/tap landings and settle times, the shadow on entry, the divider, the scrubber label and gears — every line ok before a deck change goes out, a line added when a behaviour changes. The window must be on screen: an occluded tab paints no frames and transitions stall (the first check reports it). Beyond that page, the same is done by hand in Chrome, inside an iframe of the wanted size (400×820 phone, 844×390 phone sideways, 820×1180 / 1180×820 iPad, desktop sizes) with synthetic `TouchEvent`s on the scrubber and the deck, sampling the DOM (classes, computed visibility, `data-n` of what is on top, the label's contents). The harness and the expected values per step are in `docs/superpowers/plans/2026-08-23-ipad-deck-and-scrubber.md`.

## iOS home screen app — what was learned the hard way

- **The manifest is required.** With only the legacy `apple-mobile-web-app-*` metas, iOS 26/27 launches the icon as a browser window (bottom bar, `display-mode: browser`) on every start after the first. `display: standalone` in `manifest.json` fixes it. Reinstall the icon after changing the manifest; it is read at install.
- **Plain HTTP on a LAN IP never holds standalone mode**; test installs from the real HTTPS domain.
- **Never put the sheets inside a transformed/clipping container.** Inside one, iOS resolves `bottom: 0` a status bar short and gets `100lvh` wrong too — the card ends above the glass. Sheets `position: fixed` on the viewport with `top: env(safe-area-inset-top) + …` and `bottom: …` are sized correctly. The top is handled by painting a backdrop over them instead.
- **The status bar cannot be hidden or recoloured from a web page.** iOS picks black or white text from what it renders underneath; `theme-color`, `color-scheme` and a light hairline at the top edge all changed nothing. The blur along the top of the content under the status bar is iOS too; `--top-gap` keeps it on the backdrop instead of the paper.
- **The view launches one status bar short.** The home screen app's web view starts 797 tall on a 390×844 phone and iOS grows it to the glass only if the document is taller than that view — on a first launch always, later only without a snapshot. `--app-height: 100lvh` (the large viewport, 844 from the start) does that; `100dvh` or a height read from `innerHeight` at load size the page to the short view, iOS leaves it there, and a black band stays under the sheets (17e; the 16's first launch). The correction fires only `visualViewport` `resize`, not `window` `resize` — the tap divider listens to both. Found 2026-08-28 with bare test pages carrying a viewport readout (`git log -- test.html`).
- `safe-area-inset-bottom` is 34 px on Face ID phones and the best available hint for the corner radius when the model is not in `SCREEN_RADII` (×1.62 ≈ 55 px).
